# gRPC и Telegram-прокси

## Отдельный сервер для gRPC

Запуск отложен до появления нового сервера. DNS меняет владелец домена. Предлагаемое имя: `grpc.errorclub.club`.

Рабочая связка через Cloudflare: **VLESS → gRPC → TLS → Cloudflare → новый сервер**. gRPC — транспорт, VLESS — протокол. Для этого подключения `flow` оставляют пустым. REALITY и `xtls-rprx-vision` здесь не используют; существующие подключения TCP + REALITY остаются отдельными.

1. На новом сервере установить актуальную 3X-UI. Зарезервировать TCP 443 под gRPC. Панель управления должна иметь отдельный адрес/порт.
2. Выпустить сертификат для `grpc.errorclub.club`, например публичный ACME-сертификат через DNS challenge. Закрытый ключ хранить только на сервере. Настроить автоматическое продление.
3. В панели создать VLESS inbound: порт `443`, транспорт `gRPC`, service name `vl-grpc`, TLS включён, сертификат и ключ из шага 2, ALPN `h2`, flow пустой. Значение service name одинаковое на сервере и в клиентской ссылке.
4. В Cloudflare добавить A-запись `grpc` с IPv4 нового сервера и включить проксирование (оранжевое облако). AAAA добавлять только при рабочем IPv6.
5. В Cloudflare включить **Network → gRPC**. Выбрать **SSL/TLS → Full (strict)**. На origin должен работать TLS на 443 с HTTP/2 и ALPN h2. Cloudflare Access не обеспечивает авторизацию gRPC; доступ контролирует сам VLESS.
6. Добавить тестового клиента в панели, импортировать ссылку и проверить фактический выход с нового сервера. HTTP-запрос к корню домена сам по себе не проверяет VLESS/gRPC.
7. После появления сервера подключить его к выдаче бота. На первичной панели список `XUI_INBOUND_IDS` явно задаёт VLESS inbounds, которые должны попадать в подписку. Не вставлять туда ID другой самостоятельной панели: ID локальны для панели. Сначала настроить управление удалённым узлом либо отдельную интеграцию и проверить выдачу на нём.

Не направлять этот DNS на существующие серверы до настройки нового inbound и сертификата. Доступность Cloudflare зависит от сети пользователя; текущие TCP + REALITY подключения полезно сохранить.

Требования: [Cloudflare gRPC](https://developers.cloudflare.com/network/grpc-connections/), [3X-UI v3.8.5](https://github.com/MHSanaei/3x-ui/tree/v3.8.5).

## MTProto из 3X-UI

В 3X-UI 3.8.5 MTProto обслуживает отдельный процесс `mtg-multi`, которым управляет панель. Это Telegram-прокси, не VPN для всех приложений. FakeTLS — часть MTProto; его нельзя проксировать обычной оранжевой DNS-записью Cloudflare.

Бот поддерживает явно выбранного **общего бесплатного** клиента панели. Это сохраняет прежнюю бесплатную модель MTProto. Клиенты платного VPN не привязываются к этому inbound, и Telegram-ссылка не смешивается с VPN-подпиской.

Если MTProto находится в основной панели бота, достаточно трёх настроек: ID inbound, email общего клиента и публичный хост. **ID относится к выбранной панели, а не ко всем серверам сразу.** Сам inbound без клиентов не выдаёт ссылку: в нём должен быть включённый клиент `vl-telegram-shared` с FakeTLS secret.

Для MTProto на отдельной нидерландской панели используются пять настроек в `.env` **на сервере бота**:

```dotenv
XUI_MTPROTO_INBOUND_ID=3
XUI_MTPROTO_SHARED_EMAIL=vl-telegram-shared
XUI_MTPROTO_PUBLIC_HOST=niderland.yozik.ru
XUI_MTPROTO_PANEL_BASE_URL=https://niderland.yozik.ru:10665/WEB_BASE_PATH
XUI_MTPROTO_API_TOKEN=TOKEN_FROM_NETHERLANDS_PANEL
```

`WEB_BASE_PATH` заменяется точным префиксом панели, без `/panel/inbounds` в конце. API-токен создаётся в нидерландской панели с правами `node-sync` (либо `admin`); `monitor` не разрешает читать клиентов. Это отдельный токен панели, не ключ Telegram-бота и не MTProto secret. Если `XUI_MTPROTO_PANEL_BASE_URL` пустой, бот читает основную российскую панель, как раньше. Менять `XUI_PANEL_BASE_URL` для переноса MTProto не нужно: он управляет VPN-подписками.

Порт (сейчас `1443`) и актуальный FakeTLS secret бот читает из выбранного inbound. Из всех клиентов панели выдаётся только указанный email. При недоступности панели или отключении клиента/inbound карточка сообщает о временной недоступности; кнопка с нерабочей ссылкой не выдаётся. Кэш обновляется в течение 30 секунд.

Текущая схема: нидерландский сервер, TCP 1443 → MTProto → Telegram. Публичный хост должен вести прямо на сервер, без HTTP-проксирования Cloudflare. Домена `errorclub.club` это не касается.

После изменения `.env` нужно **пересоздать контейнер**, чтобы он получил новые переменные. Обычный `docker compose restart` их не перечитывает. Новые имена переменных должны также быть перечислены в `environment` сервиса `bot` в `docker-compose.yml` (актуальная версия репозитория уже содержит их).

```bash
cd /root/vpn-bot
docker compose up -d --no-deps --force-recreate bot
docker compose ps bot
```

В мини-приложении открыть «Прокси» → «MTProto (Telegram)» → «Добавить в Telegram». Telegram покажет собственное подтверждение включения прокси. Полная проверка на пользовательском устройстве: Telegram показывает «Подключено» и загружает сообщения при выключенном VPN.

Реализация панели: [схема MTProto](https://github.com/MHSanaei/3x-ui/blob/v3.8.5/frontend/src/schemas/protocols/inbound/mtproto.ts), [управление mtg-multi](https://github.com/MHSanaei/3x-ui/tree/v3.8.5/internal/mtproto).
